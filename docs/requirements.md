# Stross 需求文档（v2：一站式设备共享）

> 版本：v2（定稿）｜状态：作为架构设计（`plugin-architecture.md` 后续版本）与
> 各阶段优化的**唯一需求输入**。与 roadmap 的差异：本文档重新定义了产品定位，
> 旧 roadmap 条目（浏览器观看端等）在本文档中被取代的部分以本文档为准。
>
> 需求 → 架构 → 优化的方法论约定：任何架构决策必须能追溯到本文档的某条需求；
> 任何优化必须服务于本文档的某条需求或非功能指标。

## 1. 定位与核心价值

> **Stross = 局域网"一站式设备共享"平台**：设备自动发现、协商后建立共享会话，
> 把本机的任何可共享能力（屏幕 / 摄像头 / 麦克风 / 系统声音 / 文件 / 剪贴板）
> 以流式或无损方式共享给目标设备。**任何设备既可是源也可是汇**（如"电脑用
> 手机的麦克风"）。全程自动发现，不手输 IP；**接收端全部原生，不依赖浏览器**。

核心价值（锚点，不随版本变化）：

- **平台无关**：协议 / 数据 / 核心层与平台无关，各平台设备（Linux / Windows /
  Android，远期 macOS / iOS）可相互共享数据；
- **零门槛连接**：打开即扫描、点选即共享，全程无 IP、无配置；
- **双向设备共享**：设备即"能力集合"，A 的能力可以接到 B 的汇上，方向任意；
- **流畅运行**：延迟 / 帧率 / 内存 / 弱网表现有可测指标（见 §6.2）。

## 2. 决策记录

需求重新定义过程中已拍板的决策，后续不得未经评审推翻：

| # | 决策 | 理由 / 影响 |
|---|---|---|
| D1 | **完全去除浏览器观看端**（移除内嵌 viewer、jmuxer/MSE 链路、`/` 观看页） | 放弃"零安装观看"价值；接收端全部原生（Tauri 原生播放 / Android 原生播放）。影响：播放技术选型成为架构关键决策（见 §10） |
| D2 | **一期先流式闭环**，无损共享二期 | 控制范围膨胀风险；一期 = 发现 + 协商 + 流式共享（正/反向）+ 原生接收 |
| D3 | **反向外设（手机当电脑麦克风）是一期核心验收场景** | 同时验证反向共享、低延迟、音频输出 Sink、原生接收四条能力 |
| D4 | 会话身份（session id）由**发起方内核统一签发**（与中继 stream_id 合一） | 消除"内核会话 / 中继流"两套并行概念 |
| D5 | 传输统计由**传输主动推送**（watch channel 周期上报）进内核聚合 | 事件驱动，避免轮询；与内核事件模型一致 |
| D6 | **桌面播放：ffmpeg 子进程解码 + cpal 输出**（H264 → rgba 原始帧、AAC → PCM；与采集侧同一 ffmpeg 二进制与子进程编排模式，**零新增原生构建依赖**） | 对称采集侧 pipeline；保持"平台无关构建"硬约束（stross-media 无原生构建依赖，Android 交叉编译不受影响）；播放实现藏在 `PlaybackSink` trait 后，未来可换 ffmpeg-next / symphonia 不惊动上层。Android 播放（1f）用 MediaCodec + AudioTrack，另行实现同一 trait |
| D7 | **控制面安全模型**（Stross 常驻运行，CLI 可像客户端一样接上异步控制）：v1 控制端点**仅绑定回环**（127.0.0.1），信任边界 = 本机 OS 用户（本机 CLI / GUI 可控，LAN 零暴露面）；**远程控制（跨设备，如手机控制电脑）留待后续阶段**——届时需要：设备配对令牌（被控端展示一次性配对码）+ **高危动作（开始摄像头/麦克风采集）被控端用户确认** + 动作审计日志 | 控制面能下发"开始采集"，滥用即监控风险，门控必须**强于**数据面；数据面保持内网可信 + 会话级 PIN（F2.5）；密钥 / 令牌**不进日志、不进 mDNS TXT、不进进程参数**（CLI 从环境变量 / 本地文件读取，避免 ps 泄露） |

## 3. 用户场景

| 场景 | 共享类型 | 方向 | 优先级 |
|---|---|---|---|
| 手机看电脑屏幕 / 视频 | 流式 | 电脑 → 手机 | 一期 |
| 手机听电脑声音 | 流式（系统音频） | 电脑 → 手机 | 一期 |
| **电脑用手机麦克风** | 流式（反向，外设化） | 手机 → 电脑 | 一期（验收） |
| 手机当电脑摄像头 | 流式（反向） | 手机 → 电脑 | 三期 |
| 文件互传 / 剪贴板同步 | 无损 | 双向 | 二期 |
| 键鼠注入 | 无损（远期 Deskflow 方向） | 手机 → 电脑 | 远期 |

## 4. 功能需求

### 4.1 发现模块（Discovery，独立模块）

- F1.1 打开即扫描局域网内所有 Stross 设备（mDNS 广播 / 浏览）；
- F1.2 每台设备广播**能力清单**（角色、可共享项、支持传输、控制端点）——mDNS TXT 携带能力描述；
- F1.3 设备列表展示**设备名 + 能力徽标**，不显示裸地址；
- F1.4 发现模块只负责"找到并引导对接"；对接完成后，**数据连接的建立与控制交给连接控制模块**。

### 4.2 连接控制（Kernel / 控制面）

- F2.1 源设备勾选"共享什么"，目标设备勾选"接收什么"——**接收端有选择权**（不是被动接收全部）；
- F2.2 **推收关系确定后才建立数据连接**（先会话、后传输）；
- F2.3 会话内可动态增删共享项、改画质、切换传输、断开会话；
- F2.4 会话身份由发起方内核统一签发（D4）；
- F2.5 会话级访问码（PIN）鉴权保留并最终落到接入层（推流 / 接收动作前校验）。

### 4.3 流式共享

- F3.1 采集：保留现有全部能力（屏幕 / 摄像头 / 麦克风 / 系统声音，ffmpeg / MediaCodec）；
- F3.2 接收：**原生播放**（D1）——视频播放、音频输出（扬声器 / 录音设备）；
- F3.3 新增**音频输出 Sink**（电脑播放手机麦克风的声音，D3 的关键能力）；
- F3.4 低延迟链路（WebRTC / SRT）与接收端抖动缓冲（见 §4.4、§7）；
- F3.5 传输多路径：WS（无损兜底）/ SRT（自适应）/ QUIC（无损多路复用）/ WebRTC（有损低延迟）按会话协商选择。

### 4.4 交互数据管理模块（SessionDataManager）

每条会话两个通道，物理隔离（复用 QUIC 双 stream / WebRTC 双 datachannel 的先例）：

- **流式通道（StreamChannel）**：媒体帧，Lossy / Adaptive 契约；
  - 接收端**抖动缓冲（jitter buffer）**：定长环形缓冲，按 seq/pts 索引与排序，
    乱序帧落槽等待、按 pts 顺序消费、超时未齐跳过并等待关键帧重对齐；内存有界 = 固定容量；
  - 推流端不设环形缓冲（采集节拍驱动，`mpsc` 足够）；
  - 中继侧保留"新观众先收最近关键帧 + Lagged 重对齐"（现有机制），与接收端抖动缓冲互补；
- **无损通道（ReliableChannel，二期）**：文件分块 / 剪贴板 / 输入事件，
  Lossless 契约；分块 + 滑动窗口 + 重传 + 校验；**不适用环形缓冲**。

### 4.5 UI 交互（PC / 手机一致）

- F5.1 PC 与手机**同一套交互流程**：
  `扫描 → 设备列表 → 本机"共享面板"勾选共享项 → 目标设备"接收面板"勾选接收项 → 确认建立 → 运行`；
- F5.2 现有"连接 → 推 / 看两 Tab"交互作废，前端流程重做
  （Tauri 桌面 + Android 共用 `apps/stross-gui/web`，技术基础已具备）；
- F5.3 运行页：实时状态（延迟 / 帧率 / 缓冲）、增删共享项、改画质、断开会话。

### 4.6 无损共享（二期）

- F6.1 文件互传（分块 + 断点续传 + 校验）；
- F6.2 剪贴板同步（文本起步）；
- F6.3 输入注入（远期，平台适配重）。

## 5. 平台无关性（硬约束）

| 层 | 含义 | 约束 |
|---|---|---|
| 协议 / 数据层 | 线上格式（24 字节帧头、JSON 控制消息、H.264/AAC 载荷）在任何平台字节级一致 | **禁止引入平台特定字段**；新协议扩展保持平台无关 |
| 核心 / 控制层 | 发现、协商、会话、路由、缓冲逻辑为纯 Rust、无平台代码 | 新增模块（SessionDataManager、jitter buffer）必须纯逻辑、可单测 |
| 适配层 | 采集 / 播放 / 渲染按平台实现，藏在 trait 后面 | 采集侧 `CaptureBackend`（已有）；**播放侧新增 `PlaybackSink` trait**，桌面与 Android 各一个实现 |

验收：**跨平台互通矩阵**——Linux PC ↔ Windows PC ↔ Android 手机任意两两共享
（屏幕 / 声音 / 麦克风反向）必须工作。

## 6. 非功能需求

### 6.1 低延迟（分场景）

| 场景 | 指标 |
|---|---|
| 屏幕共享（电脑 → 手机） | 端到端 ≤ 1–2s（WS 兜底）；< 300ms（WebRTC 路径） |
| **反向音频（电脑用手机麦克风）** | **端到端 ≤ 100–200ms（通话级）**——一期最严苛指标，倒逼低延迟编码与传输 |

### 6.2 流畅运行（可测指标）

| 项 | 指标 |
|---|---|
| 帧率稳定 | 1080p@30fps 不掉帧（本地网络） |
| 弱网韧性 | 丢包 5–10% 时画面不冻结超过 1s；断线自动重连 |
| 内存有界 | jitter buffer / 中继缓冲 / 无损滑动窗口全部固定容量，不随运行时间增长 |
| 会话响应 | 建立 < 1s；增删共享项、改画质即时生效 |

### 6.3 其它

- 安全：内网可信模型；数据面会话级访问码（PIN）落到接入层（F2.5）；控制面（CLI 接入控制）v1 仅回环绑定，远程控制需配对 + 高危动作用户确认 + 审计（D7）；
- 可维护性：分层单向依赖、核心逻辑可单测（现状已达成，65 测试全绿，需保持）。

## 7. 架构约束（需求 → 架构的推导结论）

1. **内核 = 连接控制 / 设备协同控制面**：持有设备图、会话拓扑、鉴权、事件广播；
   媒体帧与协议私有状态（分片 / ICE 等）不进内核；
2. **中继 = 受内核驱动的数据面后端**：保留流表与关键帧缓存，受内核指令建流 / 拆流，
   向内核上报事件（主从关系，非并行两套）；
3. **发现模块独立**：只管"找到 + 引导"，不碰数据；
4. **SessionDataManager 纯逻辑**：流式通道（环形抖动缓冲）+ 无损通道（滑动窗口）；
5. **PlaybackSink / CaptureBackend 对称**：采集与播放都是平台无关 trait 的平台实现。

## 8. 阶段划分与验收

### 一期：流式闭环（当前目标）

内容：发现引导 + 会话协商 + 流式共享（正 / 反向）+ 原生接收（无浏览器）+ 音频输出 Sink + 抖动缓冲。

验收：
1. PC + 手机打开即互相发现，列表显示名称与能力徽标；
2. 手机选择"接收电脑屏幕 / 声音"→ 确认 → 原生播放，全程无 IP 输入；
3. **电脑选择"接收手机麦克风"→ 确认 → 电脑扬声器 / 录音设备播放手机声音**（D3）；
4. 会话运行中可停止单项共享、断开会话；断线自动重连；
5. 移除浏览器观看页后，控制 API / 信令不受影响；
6. 跨平台互通矩阵通过（§5）。

### 二期：无损共享

文件互传 + 剪贴板同步（ReliableChannel）。

### 三期 / 远期：外设增强

手机摄像头反向、键鼠注入；macOS / iOS 接入（协议兼容性保持）。

## 9. 明确不做（YAGNI 边界）

- ❌ 浏览器观看端（含 jmuxer / MSE、内嵌 viewer、零安装观看价值）；
- ❌ 公网穿透 / 云中继 / 多流房间（内网工具定位；"多流房间"是否重议见 §10）；
- ❌ GStreamer 式流水线插件、动态加载（沿用 `plugin-architecture.md` §9）。

## 10. 遗留待定项（架构阶段处理）

| 项 | 说明 |
|---|---|
| 播放器技术选型（桌面） | **已定（D6）**：ffmpeg 子进程解码 + cpal 输出；Android（1f）：MediaCodec + AudioTrack。若 D3 反向音频延迟预算吃紧，音频解码可换 symphonia 进程内解码（备选路径，trait 已隔离） |
| 反向音频延迟预算的实现路径 | ≤ 200ms 需要低延迟编码配置 + WebRTC/SRT 传输 + 抖动缓冲 ≤ 100ms 的自适应策略 |
| "多流房间"是否重议 | 一期按"一机一流 + 会话级访问码"做；是否升级为房间 / 命名空间待一期后评估 |
| macOS / iOS 是否纳入正式平台矩阵 | 协议 / 核心层保持兼容；适配层（采集 / 播放）成本待评估 |
