## 1. 测试环境与方法

| 项 | 说明 |
|---|---|
| 拓扑 | 本机双开三进程：`serve`（接收端 PC-A：内核 + 受控中继 + 控制面）、`push`（推流端 PC-B：testsrc2 合成视频 30fps + 440Hz 测试音）、`receive`（观看端：ffmpeg 解码播放 + 延迟采样）。同机同钟校准 → 绝对延迟可测 |
| 推流方式 | 凭证接入（ShareToken），`--report-start` 记录会话起点墙上毫秒 + 首帧 pts 修正（`--calibrate` 一次读 JSON） |
| 数据面 | 三传输各自跑完整链路；SRT 走有损路径（抖动缓冲 + 关键帧重对齐），WS/QUIC 走无损直通（`channel_kind_for_url` 分流） |
| 期望值 | 帧 = SECS×30；音频块 ≈ SECS×47（AAC 定长块） |
| 断言阈值 | 接收帧 ≥90%、音频块 ≥90%、绝对延迟 p99−min（尾延迟）≤250ms、serve RSS 有界 |
| 弱网注入 | `unshare -rn` 用户/网络命名空间 + `tc qdisc add dev lo root netem loss X% delay Yms`；命名空间内 `lo` 必须 `ip link set lo up`（默认 DOWN，否则链路不可达）。netem 双向生效：RTT 实测 = 2×delay（40ms / 80ms） |

## 2. 长跑稳定性（300s × 3 传输，期望 9000 帧 / 14100 音频块）

| 传输 | 接收帧 | 音频块 | 绝对延迟 min / p99 | 相对附加延迟 p90/p95/p99/max | serve RSS | 判定 |
|---|---|---|---|---|---|---|
| srt | 8941/9000（99.3%） | 13993/14100（99.2%） | 240.9 / 244.8 ms | 0.7 / 0.9 / 1.6 / 8.6 ms | 30208 → 32624 KB | ✅ |
| quic | 8928/9000（99.2%） | 13973/14100（99.1%） | 0.2 / 3.8 ms | 0.9 / 1.2 / 1.5 / 13.8 ms | 30632 → 32332 KB | ✅ |
| ws | 8928/9000（99.2%） | 13974/14100（99.1%） | 0.0 / 1.8 ms | 0.5 / 0.6 / 0.8 / 1.6 ms | 30648 → 31996 KB | ✅ |

结论：

- **三传输 300s 长跑全部达标**；帧差 ~60–70（<1%）为接入窗口（握手 + ffmpeg 预热 + TSBPD 缓冲建立）内的正常丢失。
- **绝对延迟分层符合设计**：ws/quic 直通（min ≈ 0ms）；srt 固定 +240ms ≈ 两级 TSBPD 缓冲（默认 `rcv_latency` 120ms × 推/收两端）买来的丢包稳定性。
- **相对附加延迟（抖动/尾延迟）三传输 p99 ≤ 1.6ms**：稳态下传输层无多余抖动，抖动缓冲未引入排队。
- **RSS 全程有界**：单会话 300s 服务端内存增量 ≤ 2.4MB，无泄漏迹象；接收端 `--no-write` 免 tmpfs 落盘压力。

## 3. 弱网诊断（60s × 3 传输 × 2 场景，期望 1800 帧 / 2820 音频块）

### 3.1 轻度弱网：丢包 5% / 延迟 20ms（RTT 实测 ~40ms）

| 传输 | 接收帧 | 音频块 | 绝对延迟 min / p99 | 相对附加延迟 p99/max | 尾延迟 p99−min | 判定 |
|---|---|---|---|---|---|---|
| ws | 1728/1800（96.0%） | 2727/2820（96.7%） | 40.3 / 336.9 ms | 281.7 / 347.6 ms | 296.6 ms | ❌ 尾延迟超限 |
| srt | 1697/1800（94.3%） | 2736/2820（97.0%） | 280.4 / 284.4 ms | 1.5 / 29.2 ms | 4.0 ms | ✅ |
| quic | 1729/1800（96.1%） | 2727/2820（96.7%） | 41.7 / 1311.8 ms | 947.3 / 1042.0 ms | 1270.1 ms | ❌ 尾延迟超限 |

### 3.2 中度弱网：丢包 10% / 延迟 40ms（RTT 实测 ~80ms）

| 传输 | 接收帧 | 音频块 | 绝对延迟 min / p99 | 相对附加延迟 p99/max | 尾延迟 p99−min | 判定 |
|---|---|---|---|---|---|---|
| ws | 1696/1800（94.2%） | 2682/2820（95.1%） | 81.0 / 1586.7 ms | 1374.2 / 1907.2 ms | 1505.7 ms | ❌ 尾延迟超限 |
| srt | 1249/1800（69.4%） | 2675/2820（94.9%） | 320.7 / 325.0 ms | 2.1 / 26.6 ms | 4.3 ms | ❌ 视频帧不足 |
| quic | 534/1800（29.7%） | 1543/2820（54.7%） | 1970.6 / 27712.5 ms | 10441.4 / 11509.6 ms | 25741.9 ms | ❌ 全面劣化 |

结论（诊断基线，弱网下未达标为预期，用于调参决策）：

- **SRT 是弱网唯一可用通道**：5% 丢包下绝对延迟纹丝不动（min 280 → p99 284ms，尾延迟仅 4ms），画面/音频连续（94%+）；丢包由 ARQ 重传 + TSBPD 缓冲吸收，表现为"延迟换稳定"。
- **WS/QUIC 帧率靠重传保住，但尾延迟秒级**：TCP/QUIC 丢包恢复是"偶发大停顿"模式（一处丢包 → 重传等待 → 瞬时卡顿），正是流媒体最怕的体验形态；QUIC 在 10% 丢包下拥塞窗口退避近乎停滞（p99 达 27s 级）。
- **10% 丢包/40ms 是 SRT 临界点**：ARQ 重传往返 80ms 无法在 240ms 缓冲窗口内补齐 → 跳洞 + 关键帧重对齐 → 视频帧跌至 69%（音频仍 95%，音频轨无 keyframe 依赖）。**B4 调参方向：上调 `SrtOptions` 的 `rcv_latency`（默认 120ms × 两端）或放宽 ARQ 参数**，可显著改善 10% 丢包档位。

## 4. 测试过程中发现并修复的问题

1. **`latency-stability-test.sh` 变参解析 bug**：`TRANS` 只取 `$2`（`TRANS="${2:-srt quic}"`），与文档宣称的 `[SECS] [TRANS...]` 不符 → 此前 30s/300s 测试**实际只跑了 srt**，quic/ws 从未被覆盖；改为真变参（`shift 1` + `TRANS="${*:-srt quic}"`）。
2. **`unshare -n` 命名空间 lo 默认 DOWN**：ping "网络不可达"、TCP 连接失败、mDNS 报 `Network is unreachable`（服务可 bind 但连不上）→ 弱网脚本先 `ip link set lo up`。
3. **遗留 `[DBG]` 日志**：`relay/mod.rs` handle_watch 两行、`srt.rs` send 两行（插桩残留）→ 已清理。
4. **SRT 回归根因**（本轮修复对象，已在 `ebfc5bd` 记录）：CLI receive 从硬编码 Lossless 改为 `channel_kind_for_url`（srt → Lossy）后暴露 JitterBuffer 三缺陷（音频轨跳洞死循环 u32 环绕 / 视频轨跨轨共享 seq 占位空洞吞帧 / 跳洞游标落后被关键帧清空）→ 终案为 StreamChannel 按轨归一化 seq + 跳洞上限 + `highest_seq` 上界。

## 5. 结论与下一步

- **当前基线**：局域网 300s 长跑三传输稳定（帧/音频 ≥99%、RSS 有界、相对抖动 p99 ≤1.6ms）；弱网仅 SRT 可用，5% 丢包档达标、10% 丢包为临界。
- **下一步（B4）**：SRT `rcv_latency`/ARQ 弱网调参 + 弱网专项回归；弱网/长跑自动化脚本已就绪（`weaknet-test.sh` / `latency-stability-test.sh`），阶段 C 弱网验证可复用。
